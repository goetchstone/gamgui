# Domain: Build & Packaging

**One line:** Vendors the GAM7 binary (checksum-pinned), hash-locks the Python dependencies, regenerates the browse catalog, precompiles the UI's Tailwind CSS with a checksum-pinned CLI, and builds the codesigned macOS `.app` — plus the drift guards that fail CI when any pin/count goes stale.

**Owns invariant(s):** #7 (the vendored GAM pin fails closed — an asset with no committed SHA-256 is refused, `--allow-unpinned` is CI-preview only). Also owns the three drift guards named in CLAUDE.md.
**Enforcement home:** `tests/test_workflow_safety.py` (no expression inside a `run:` script; every action pinned by commit SHA; CI keeps the coverage gate; CI builds the `.app` from the pinned GAM and runs `check_app.py` on it), `tests/test_build_css.py` (the Tailwind CLI's fail-closed pin, hermetic; every mapped platform pinned; the committed `app.css` carries the pinned version's banner and, where the CLI is cached, is what it builds; CI's lint job runs the check; `build_app.sh` rebuilds the CSS before freezing), `tests/test_fetch_gam.py` (the fail-closed gate, hermetic; also `test_ci_only_grants_the_opt_in_to_the_preview_job` and `test_pywebview_is_pinned`), `tests/test_locks.py` (the locks match pyproject, cover every input, stay universal and hashed; CI and `build_app.sh` install nothing else; Dependabot uses the uv ecosystem), `tests/test_command_contract.py` (`test_required_command_tokens_present`, `test_catalog_matches_grammar`, `test_pinned_version_consistent`), `tests/test_bump_gam.py` (bump edits still match their targets), `tests/test_build_signing.py` (hardened runtime on every signature, the sign order, minimal entitlements, `gam.entitlements` == the vendored binary's, `check_app.py`'s module list and pin regex still match the source), `scripts/check_app.py` (CI's `app` job: the built bundle itself), `tests/test_polish.py` (the stated counts/pin/floor stay true — `test_docs_state_the_real_catalog_counts` for CLAUDE.md, README and ROADMAP, `test_claude_md_states_the_current_gam_pin_and_python_floor`).

## Files
- `Makefile` — `venv` (auto-picks newest `python3.1x` ≥3.10; system 3.9 is refused), `setup` (`venv`, then the locked pip from `requirements/pip.txt`, then `dev.txt` + `app.txt` in one `--require-hashes --build-constraint requirements/app.txt` resolve, then the project with `--no-deps --no-build-isolation -e .`), `setup-latest` (`venv`, then pyproject's flexible ranges, unhashed — the only target that installs them), `gam`→`fetch_gam.sh`, `css`→`build_css.sh`, `test`, `cov`→the suite under `--cov` with the `fail_under` floor in `[tool.coverage.report]` (what CI's macOS 3.14 leg runs), `lock`→`uv pip compile` of both locks (`ARGS=--upgrade` refreshes every pin), `lint`→`ruff check .`, `mypy`, then `build_css.sh --check` (the same checks as CI's `lint` job; rule set, `[tool.mypy]` and the exact ruff/mypy pins in `pyproject.toml` — bug-catching rules only, ruff's formatter deliberately not adopted; mypy covers `gamgui/core` + `gamgui/web` at `check_untyped_defs`, checked as `platform = darwin` / py3.10 even on CI's Linux runner, with only the optional `abapit` import exempt from stubs), `run`, `app`→`build_app.sh`.
- `requirements/app.in` / `requirements/dev.in` / `requirements/pip.in` → `requirements/app.txt` / `requirements/dev.txt` / `requirements/pip.txt` — the hash-locked dependencies. `app` is what the `.app` ships (pyproject's runtime deps + the `desktop` extra) plus the exact PyInstaller; `dev` is runtime + the `dev` extra + the build backend (`hatchling`, and the `editables~=0.3` its `get_requires_for_build_editable` asks for), what CI runs; `pip` is only `pip>=25.3`, installed first by `make setup` and `build_app.sh`. The `.in` files repeat pyproject's requirements (`test_lock_inputs_list_what_pyproject_declares`); pyproject stays the flexible source for `make setup-latest`. `make setup` installs dev and app in one resolve, so the two must pin every shared package alike (`test_dev_and_app_locks_agree_on_every_shared_pin`).
- `scripts/fetch_gam.sh` — downloads the GAM7 macOS asset for this arch, verifies SHA-256 against the pin **before extracting**, installs into `gamgui/resources/gam7/`, writes `VERSION` + `SHA256`. Its `TAG` must equal `EXPECTED_GAM_VERSION` (`test_pinned_version_consistent`).
- `scripts/gam_checksums.txt` — the committed pin: `<sha256>  <asset-filename>`. One line today.
- `scripts/bump_gam.py` — the whole "Updating GAM" runbook as one command: attest → pin → vendor → bump version strings + mock → regen catalog → refresh the counts in CLAUDE.md, README and ROADMAP. Opens a PR in CI.
- `scripts/build_command_catalog.py` — parses `GamCommands.txt` via `parse_grammar` → writes `command_catalog.json` stamped with `EXPECTED_GAM_VERSION`.
- `scripts/build_app.sh` — PyInstaller build of `dist/GamGUI.app`; auto-vendors GAM if missing; rebuilds `app.css` (`build_css.sh`) so the bundle's CSS matches its templates; creates a fresh `build/venv` from `$PYTHON` (default `.venv/bin/python`, the interpreter it freezes), installs the locked pip (`requirements/pip.txt`) and then only `requirements/app.txt` into it with `--require-hashes`, the same file as `--build-constraint`; picks the stable "GamGUI Local" identity (else ad-hoc) and hands off to `sign_app.sh`.
- `scripts/check_app.py` — smoke-checks a built bundle without launching it; run with the build venv's Python (`build/venv/bin/python scripts/check_app.py dist/GamGUI.app`, it needs that venv's PyInstaller). Checks: `CFBundleExecutable` exists and is executable; `codesign --verify --deep --strict`; the hardened-runtime flag on the app and on `gam`; the entry script and, via `CArchiveReader(...).open_embedded_archive(<the PYZ entry>)`, every `gamgui` source module (bar `NOT_FROZEN`) plus the modules loaded by name at runtime (`DYNAMIC`: uvicorn's loop/protocol/lifespan, `keyring.backends.macOS`, `webview.platforms.cocoa`, `python_multipart`, pyobjc); every template and static file, `GamCommands.txt` and a `command_catalog.json` stamped with the pin, all under `Contents/Frameworks` (the `.app`'s `sys._MEIPASS`); and the bundled `gam version` reporting `GAM <pin>`, run with a throwaway `HOME`/`GAMCFGDIR` and a bare `PATH`.
- `scripts/sign_app.sh` — signs a built bundle with the hardened runtime: `--deep` app sign, then `gam` with its own entitlements, then a shallow reseal; `--verify --deep --strict`. Runs alone on a built `.app` (`scripts/sign_app.sh dist/GamGUI.app -`).
- `scripts/app.entitlements` / `scripts/gam.entitlements` — the app gets `disable-library-validation` only; `gam` gets upstream GAM's own set (`allow-jit`, `allow-unsigned-executable-memory`, `disable-library-validation`).
- `scripts/vendor_assets.sh` — vendors htmx (SRI-verified) into `web/static/vendor/`, so no remote scripts load.
- `scripts/build_css.sh` — `make css`: builds `gamgui/web/static/app.css` with the Tailwind standalone CLI `TAILWIND_VERSION` (v3.4.17, the version the retired in-browser Play CDN ran). The CLI is fetched by a URL built from the pin (no release-JSON lookup), cached in `build/tailwind/<tag>/<asset>`, and hashed against `scripts/tailwind_checksums.txt` on every run: no pin → exit 1 before any download, a mismatched download → exit 1, a mismatched cache → discarded (and re-fetched, or exit 3 under `--no-fetch`). `--check` builds to a temp file and fails if the committed CSS differs.
- `scripts/tailwind_checksums.txt` — `<sha256>  <tag>/<asset>` for macos-arm64/x64 and linux-x64/arm64, from the release's own `sha256sums.txt` (macos-arm64 and linux-x64 also checked against downloads).
- `tailwind.config.js` (repo root) + `gamgui/web/tailwind.css` (the input) → `gamgui/web/static/app.css`, **committed**, so running from source needs no CLI. The config holds the brand theme that used to sit inline in `base.html`; its content globs are every template, every non-vendor static JS file and `gamgui/**/*.py` minus `gamgui/resources/**` (gitignored GAM, differs per machine).
- `gamgui.spec` — PyInstaller spec (`main.py` entry, bundles `web/templates`, `web/static` (so `app.css`) and `resources/gam7`, pyobjc/webview via `collect_all`).
- `gamgui/resources/gam7/` — the vendored, **gitignored** binary + `GamCommands.txt` grammar + generated `command_catalog.json`.

## How it works
`make gam` runs `fetch_gam.sh`, which queries the GitHub release JSON, picks the highest-`macosNN` `.tar.xz` for `uname -m`, hashes it, and looks up `<asset-name>` in `gam_checksums.txt`. Match → install; no pin → **exit 1** (fail closed); mismatch → exit 1 always (even with `--allow-unpinned`). After a fetch the catalog is stale, so `build_command_catalog.py` must re-run. `bump_gam.py` chains all of this: it downloads, runs `gh attestation verify` (the trust anchor that lets it write the pin automatically without becoming trust-on-first-use; `attest_argv` pins the signer to `GAM-team/GAM/.github/workflows/build.yml`, `--source-ref refs/heads/main` and `--deny-self-hosted-runners`), writes the pin, re-vendors, and rewrites `EXPECTED_GAM_VERSION` (commands.py), `TAG` (fetch_gam.sh), the mock's `gam version`, and the catalog counts in CLAUDE.md/README/ROADMAP via regex `_sub`/`_sub_numbers` (refusing to guess if a pattern no longer matches). At runtime `runner.py` resolves `gam` via env override (source checkout only — ignored when `sys.frozen`) → `sys._MEIPASS/resources/gam7/gam` (bundled `.app`) → repo source tree.

## Invariants & the failure history
- **#7 fail-closed pin.** The asset name comes from the release JSON the script just downloaded, so "no pin for this name" is exactly what renaming an asset produces — treating it as trust-on-first-use would make the pin decorative, and the bundled `gam` can impersonate any domain user via DWD. Verified *before* extraction. `--allow-unpinned` exists only for the `gam-latest-preview` CI job (`test_ci_only_grants_the_opt_in_to_the_preview_job` asserts the pinned `gam-compat` job never gets it).
- **Three drift guards.** `test_pinned_version_consistent` (fetch TAG + mock all == `EXPECTED_GAM_VERSION`), `test_catalog_matches_grammar` (catalog version + command count == a fresh `parse_grammar`), `test_required_command_tokens_present` + `test_builder_commands_match_a_grammar_line` (every keyword any builder can emit is a word in `GamCommands.txt`, and every command's leading words match a real `gam …` line — generated by calling each builder, see the gam-commands runbook; skip on a clean clone, run in `gam-compat` CI after a real fetch). Bump step 1 (`fetch_gam.sh` with a new TAG but old pin) **fails by design**.
- **The stated catalog counts are load-bearing.** Two agent-facing docs once claimed only the 26 curated commands run (over 500 do) — a reviewer agent then flagged correct `readbuilder` code. `test_polish.py::test_docs_state_the_real_catalog_counts` turns the claims in CLAUDE.md, README and ROADMAP into something CI fails on, and `bump_gam.py`'s `refresh_doc_counts` rewrites them on a bump (`test_bump_patterns_still_match_their_files` keeps its patterns matching).
- **No `${{ }}` inside a workflow `run:` script.** Actions substitutes expressions into the script text before the shell parses it, so `gam-watch.yml` once ran `bump_gam.py "v${{ steps.check.outputs.latest }}"` — an upstream release tag became shell code in a job holding `contents: write`. Values reach scripts through `env:`, and the check step admits only a tag matching `^[0-9]+(\.[0-9]+){2,3}$` (bash `=~`, so a newline can't forge a second `$GITHUB_OUTPUT` line). `tests/test_workflow_safety.py` scans every workflow's `run:` blocks.
- **The attestation names the signer, not just the repo** (C6, 2026-09-24). `--repo GAM-team/GAM`
  alone accepts provenance signed by *any* workflow in that repo, from any ref — a test or PR
  workflow, or a branch run. GAM's release assets are signed by `build.yml` on `main`, on a
  GitHub-hosted runner (the certificate's SAN and runner extension, checked on 7.47.00, 7.48.00,
  7.48.11 and 7.48.12), so `attest_argv` requires exactly that. If GAM-team moves or renames its
  build, verification fails, the bump fails closed, and no PR opens: read the new attestation's
  `builder.id` (`gh api repos/GAM-team/GAM/attestations/sha256:<digest>`) and update
  `SIGNER_WORKFLOW`/`SOURCE_REF` deliberately. `test_attestation_trusts_only_gam_teams_release_workflow`.
- **Every action pinned by commit SHA** (C4, 2026-09-24). A tag is mutable — whoever controls
  `actions/checkout` or `github/codeql-action` can move `v7` to new code — and `gam-watch.yml`'s job
  holds `contents: write` + `pull-requests: write`. So every `uses:` is `owner/repo@<40-hex> # vX.Y.Z`
  (`test_every_action_is_pinned_by_commit_sha`). Dependabot's `github-actions` ecosystem reads the
  trailing version comment and moves the SHA and the comment together. To pin a new action by hand:
  `gh api repos/<owner>/<repo>/git/ref/tags/<vX.Y.Z>`, and if its `object.type` is `tag` (annotated),
  `gh api repos/<owner>/<repo>/git/tags/<that sha>` for the commit it points at.
- **Hardened runtime on the app and on `gam`** (2026-09-23). Without it dyld honors `DYLD_*` launch variables, so a same-user `launchctl setenv DYLD_INSERT_LIBRARIES=…` loads code into the app the Keychain trusts, or into the `gam` holding the plaintext credentials; until then the bundle and `gam` were signed with no runtime flag at all. Signing order matters: `codesign --force --deep` re-signs every nested Mach-O with the app's options — the old script signed `gam` *before* the deep sign, which silently replaced it (checked on a copy). So `sign_app.sh` signs `gam` after the deep sign and then reseals the bundle without `--deep`.
- **Entitlements, and why each is there.** A self-signed or ad-hoc signature has no Team ID, and library validation refuses any dylib whose Team ID differs from the process's — every bundled one, the frozen Python included — so both need `disable-library-validation` (measured: a hardened ad-hoc binary could not load its own ad-hoc dylib without it; with it, `DYLD_*` stayed ignored). The app needs nothing else: ctypes and pyobjc callbacks use the system libffi, whose arm64 closures need no writable-executable memory, and WKWebView runs its JavaScript JIT in WebKit's own process — both checked with a hardened copy of the build Python. `gam` carries upstream's set unchanged because we replace upstream's signature; `test_gam_entitlements_match_the_vendored_upstream_binary` fails if a bump changes it. Never add `allow-dyld-environment-variables`, `get-task-allow`, `cs.debugger` or `disable-executable-page-protection` (`test_no_entitlements_reopen_injection_or_debugging`). With a Developer ID (D1) every file would share a Team ID and `disable-library-validation` could go.
- **pywebview/pyinstaller pinned.** Both go inside the shipped bundle; an unpinned floor would ship an unreviewed WKWebView host or bootloader. `test_pywebview_is_pinned` (in `test_fetch_gam.py`) checks pywebview's exact pin in `pyproject.toml` equals `requirements/app.in`'s, that `app.in` pins PyInstaller exactly, and that `build_app.sh` names no package of its own.
- **`make setup` installs the locks too (review 2: R1, 2026-09-25).** C3 hash-locked CI and the `.app`, but `make setup` — README's start path, `make setup && make gam && make run` — still installed pyproject's ranges with no hashes, and `pip install -U pip` from the index; so the venv that loads the Keychain credentials when an operator runs from source held an unchecked stack. It now installs `requirements/pip.txt`, then `dev.txt` + `app.txt`, all `--require-hashes`, and the project `--no-deps --no-build-isolation` (so hatchling comes from the dev lock, not an isolated-build download). `make setup-latest` keeps the flexible install. `test_make_setup_installs_only_the_hash_locked_deps`.
- **Hash-locked dependencies (C3, 2026-09-24).** Until then CI installed pyproject's ranges (`pip install -e ".[dev]"`), the pinned `requirements.txt` was unused and missing `pytest-timeout`/`pytest-cov`, and `build_app.sh` froze whatever the dev venv held — which put uvicorn's optional `uvloop`, `httptools`, `websockets`, `watchfiles` and PyYAML in the bundle, none of which CI ever ran. Now CI installs `requirements/dev.txt` with `--require-hashes --only-binary :all:` (no package built from source, no unpinned build backend fetched; the project itself isn't installed — pytest's `pythonpath` and mypy's `files` find it) and the `.app` is built from `requirements/app.txt` alone, in a venv of its own. **uv, not pip-tools:** `pip-compile` resolves for the interpreter and OS it runs on, so the CI matrix (Linux + macOS × 3.10/3.12/3.14) would need six locks — a 3.14 lock lacks the `python_version < "3.11"` backports (`exceptiongroup`, `tomli`, `backports.asyncio.runner`) and one made on macOS lacks keyring's Linux-only `SecretStorage`/`jeepney`. `uv pip compile --universal --python-version 3.10` writes one file with environment markers that installs on all six (checked by cross-installing it for each target). **Dependabot uses the `uv` ecosystem:** its `pip` ecosystem regenerates a compiled file with `pip-compile`, which has no `--universal`, and would silently hand back a one-Python lock; the uv one re-runs `uv pip compile` with the header's `--universal`, `--generate-hashes` and `--python-version` (dependabot-core `uv/.../compile_file_updater.rb`). It needs each `.txt` next to a same-named `.in`.
- **CI builds the `.app`** (C5, 2026-09-24). Until then nothing in CI froze it: a `gamgui.spec`,
  `requirements/app.txt` or signing change that broke the bundle surfaced only at the next local
  `make app`, and CI never ran the bundle's own `gam`. The `app` job in `ci.yml` (macos-latest,
  20-minute timeout) vendors the pinned GAM with `fetch_gam.sh` (what `make gam` runs, never
  `--allow-unpinned`), restores the committed `command_catalog.json` that the fetch wiped (it is
  byte-identical to a regeneration at the pin), runs `build_app.sh` with `PYTHON=python` (the runner
  has no signing identity, so the build takes its ad-hoc branch, hardened runtime unchanged) and then
  `check_app.py` with the build venv's Python. `test_ci_builds_and_smoke_checks_the_app` keeps that
  shape. It does not launch the app — a WKWebView window needs a logged-in GUI session.
- **Precompiled CSS (U14, 2026-09-24).** Until then `base.html` ran Tailwind's in-browser JIT
  (`static/vendor/tailwind-play.js`, a 400 KB versionless snapshot) with an inline config: every
  page compiled its CSS at load, and the console warned it was not for production. The CLI is pinned
  like GAM is (invariant #7's shape: committed SHA-256 per asset, refused when absent), and CI's
  `lint` job (linux-x64) re-runs it with `--check`. The output is **not minified**: `--minify`
  rewrites colours lossily (with default targets translucent colours became rounded `hsla()`, brand
  gray `/40` one shade off; with modern targets alpha quantized to 1/255). Unminified, 17 screen
  states driven in headless Chrome matched the Play CDN build in every element's computed style
  (incl. `::before`/`::after`/`::placeholder`), bar one prefixed alias Chrome ignores
  (`transition-colors` no longer lists `-webkit-text-decoration-color`), and pixel for pixel wherever
  the page text was the same (Home shows the mock `gam` path, Calendars the index's age); 8 Tab stops
  on 5 screens kept identical focus styles. A readable file also makes each `make css` diff
  reviewable. The
  `<link>` sits after `base.html`'s inline `<style>`, where the Play CDN injected its sheet, so the
  cascade is unchanged. The linux-x64 CLI (run under Docker) wrote the same bytes as macos-arm64.


## Gotchas / mock-lies traps
- **The catalog, the drift guards and the strict mock are the only GAM checks that run offline.** `mock_gam.sh` has a grammar-shaped handler per write and fails anything unhandled, but those handlers are hand-written and its outputs canned — it cannot prove GAM accepts a command. The real syntax source of truth is the vendored grammar `gamgui/resources/gam7/GamCommands.txt`; the grammar contract checks our argv's words and leading command words against it — not option order, and not a live run.
- **A green `pytest` never proves a GAM write works** (CLAUDE.md invariant #2 / "the mock lies"). After a bump: skim `GamUpdate.txt` for breaking changes and run `scripts/acceptance.py` (read-only) against a real tenant — `bump_gam.py` deliberately omits both because they need judgment, not mechanism.
- **`make gam` wipes `resources/gam7/` (`rm -rf $DEST`)**, including the generated `command_catalog.json` — always regenerate it (or `git checkout` it, at the pinned version), or `test_catalog_matches_grammar` goes red on a count mismatch. `build_app.sh`'s own auto-vendor path does the same, and would bundle no catalog (the app then falls back to a slower live parse with no version stamp); `check_app.py` fails such a bundle.
- **The pinned `gam` needs macOS ≥ 26.5 to start.** The `gam` executable targets macOS 11.0, but GAM 7.48.11's bundled `libpython3.14.dylib` and extension modules target 26.5 (`otool -l`, `minos`), and dyld refuses a library built for a newer macOS than the one running (not reproduced here — this Mac runs 26.6.2). `macos-latest` was macOS 26.6.2 (image 20260907) when the `app` job went in; the job's `gam version` step is what would say so if a runner or a GAM bump moved that line. `fetch_gam.sh`'s own closing `gam version` swallows failure, so `gam-compat` never noticed.
- **macOS-only vendoring.** `fetch_gam.sh` uses BSD `find -perm +111`; `test_fetch_gam.py` only asserts a completed install on Darwin (it still checks the gate on Linux). System `/usr/bin/python3` (3.9) cannot install the venv.
- **A package that ships only as source needs its build backend in the app lock.** `proxy-tools` (a pywebview dependency) has no wheel, so pip builds it; `--build-constraint requirements/app.txt` makes that build install the locked, hashed `setuptools`, and a build dependency missing from the lock fails the build (hash-checking mode) rather than downloading unchecked. `--build-constraint` needs pip ≥ 25.3 — an older one fails with "no such option", and the pip bundled with a python.org 3.12.10 is 25.0.1 (uv's 3.10: 23.0.1) — so `build_app.sh` and `make setup` first install the pip locked in `requirements/pip.txt` (any pip can: it is a hashed wheel, no build). Review 2 (R8, 2026-09-25) caught `make app` failing on 3.10–3.12 before that step existed; CI's `app` job builds only with 3.14. CI's dev lock has no source-only package, so CI uses `--only-binary :all:` instead and works with any pip.
- **`make lock` keeps existing pins** — uv prefers what the `.txt` already holds; `make lock ARGS=--upgrade` (or `ARGS="--upgrade-package starlette"`) moves them. After editing a dependency, change pyproject **and** the `.in`, then `make lock`; `test_locks.py` fails on either half left behind.
- **A class the content globs can't see is not in `app.css`.** The Play CDN styled whatever the live DOM carried; the prebuilt file holds only literal class names found in the templates, non-vendor static JS and `gamgui/**/*.py`. Never assemble a class from parts (`'bg-' + tone`); write every full name somewhere (a Jinja ternary of two literals is fine). After adding one, `make css` and commit `app.css` — CI's `lint` job fails otherwise, and so does `test_committed_css_is_current` once `make css` has cached the CLI (it skips when the CLI isn't cached, e.g. in CI's test legs).
- **Bump `_write_pin` keeps only non-`gam-` lines + the new pin** — it replaces the single active GAM pin rather than appending, so `gam_checksums.txt` holds one asset line at a time.

## Testing / live-verification status
- `tests/test_fetch_gam.py` — hermetic: copies the script into a throwaway root, drives it with a stub `curl` on PATH, real `.tar.xz`; never touches api.github.com or the real `resources/gam7`. Covers refuse-unpinned, opt-in install, matching pin, mismatch-always-refuses, unknown-flag, and static branch/CI assertions.
- `tests/test_build_css.py` — hermetic like `test_fetch_gam.py` (a stub `curl` serving a fake CLI into a throwaway root): refuse-unpinned before any download, mismatch caches nothing, the pinned URL and cache path, `--check` on a stale file, a tampered cache discarded without being run, `--no-fetch` never downloads. Static: every platform the script maps is pinned, `app.css` carries the pinned version's banner, CI and `build_app.sh` run the script, the spec bundles `web/static`. The real CLI's output was checked by pixel and computed-style diff against the Play CDN build (see U14 above); a scratch PyInstaller build of `gamgui.spec` (the dev venv's PyInstaller, unsigned, outside `dist/`) held a byte-identical `app.css`, and CI's `check_app.py` checks every static file is in the bundle.
- `tests/test_bump_gam.py` — unit-tests the pure text transforms (`select_asset`, the regex rewrites) and the attestation argv so a future rename fails here instead of no-op'ing in CI. Network/subprocess orchestration is not covered.
- `tests/test_command_contract.py` + `tests/test_polish.py` — the drift/consistency guards above. All run in the offline `pytest` suite; the whole suite re-runs in the `gam-compat` CI job (the committed catalog restored after the fetch), so the token/catalog tests and the end-of-session argv sweep (gam-runner runbook) run there against a freshly fetched real binary.
- `tests/test_build_signing.py` — static: `sign_app.sh`'s runtime flag and sign order, `build_app.sh` signing only through it, the entitlement sets; on macOS with `gam` vendored, `gam.entitlements` against `codesign -d --entitlements` of the vendored binary (reads the signature, never runs `gam`).
- **Coverage gate** (T6, 2026-09-24) — CI's macOS 3.14 test leg runs `pytest -q --cov` and fails below
  `fail_under` (90; a clean clone measured 90.5% of 5,357 lines, the working tree with GAM vendored
  90.7%). One leg only: Linux skips the macOS filesystem tests and its total was never measured.

## To do common tasks here
- **Bump GAM:** `python scripts/bump_gam.py vX.Y.Z` → `.venv/bin/python -m pytest -q` → skim `GamUpdate.txt` → `scripts/acceptance.py` on a tenant. (Manual path: edit pin in `gam_checksums.txt`, `make gam TAG=vX.Y.Z`, run `build_command_catalog.py`, bump `EXPECTED_GAM_VERSION`/`TAG`/mock and the counts in CLAUDE.md, README and ROADMAP.)
- **A new builder command's contract:** nothing to list — the grammar contract calls every `GAMCommands` builder. Only an argument the builder validates needs its values in `ENUM_ARGS` (`tests/test_command_contract.py`).
- **Change a dependency:** edit `pyproject.toml` and the matching `requirements/*.in` (an `.app` dependency goes in `app.in`, a test/lint tool in `dev.in`, a runtime one in both), `make lock`, commit the `.in` and `.txt` together, then `make test`.
- **Change the bundled `.app` (deps, plist, signing):** edit `gamgui.spec` (datas/hiddenimports/plist), `requirements/app.in` + `make lock` (deps, PyInstaller), `scripts/build_app.sh` (identity) and/or `scripts/sign_app.sh` + the `.entitlements` (signing), then `make app`. If a hardened build won't launch, `log show --last 5m --predicate 'sender == "AMFI" OR process == "dyld"'` names the refused library or entitlement.
- **Bump htmx:** edit `HTMX_VER`/`HTMX_SRI` in `scripts/vendor_assets.sh`, re-run it, update the `<script>` tag in `web/templates/base.html`.
- **Add or change a Tailwind class / the theme:** edit the template (or `tailwind.config.js`), `make css`, commit both. `make css` fetches the pinned CLI on first use.
- **Bump Tailwind:** stay on v3 unless you mean to migrate (v4 drops `tailwind.config.js` and renames utilities). Take the new release's `sha256sums.txt`, check the hash of at least your own platform's download, replace the lines in `scripts/tailwind_checksums.txt`, set `TAILWIND_VERSION` in `build_css.sh`, `make css`, then diff the main screens before/after in headless Chrome.
