# Domain: Guard & Audit

**One line:** The confirmation gate that decides how hard a mutation must be confirmed and checks, server-side, that the POST carried it; and the append-only redacted JSONL log that durably records every mutation the tool ran.

**Owns invariant(s):** #2 (the guard is the mandatory middle of the mutation chokepoint — `evaluate` decides, `enforce` checks the posted form in the apply route); #4 in part (redact_argv keeps Keychain-class secrets out of the log); the audit retention bound is the same "bound anything durable/polled" discipline as #9.
**Enforcement home:** `tests/test_guard.py` (gating rules + `enforce`), `tests/test_write_routes_guarded.py` (tripwire: every POST route is exempt-with-reason or refuses a bare POST with zero `gam` writes, and its rendered confirm step runs the write; every write control has `hx-disabled-elt`), `tests/test_audit.py` (redaction + 0600 + tail), `tests/test_onboarding.py` (a secret echoed on a failed `create_user` stays out of `audit.jsonl` and the UI), `tests/test_audit_web.py` (rotation, generation spanning, mid-read snapshot), `tests/test_command_contract.py` (every `audit.record(` and every `run_authenticated(` call site is the chokepoint, a named exception, or a read). No drift guard — these are behavioral tests, not contract tests.

## Files
- `gamgui/core/guard.py` — `evaluate(previews) -> GuardDecision`; pure, no GAM call. Decides confirm / typed-confirm / hard-cap warning from a list of `ChangePreview`. `enforce(previews, form, confirm_step=False) -> Optional[str]` is the server-side half: the refusal message when the posted form lacks what the decision requires (`confirmed=1`; typed `confirm` for destructive+bulk; `confirm_step=True` demands `confirmed=1` whatever the count). `changes(targets, risk, summary)` builds previews for a route whose connector call builds its own argv.
- `gamgui/core/audit.py` — `redact_secrets` (by value), `redact_argv` (positional), `AuditLog.record(secrets=)`, rolling (`_roll_if_large`, `generation_paths`), and reverse-streaming readers (`iter_records`, `read_records`, `tail`).
- `gamgui/core/connectors/base.py` — defines `RiskLevel` (IntEnum READ_ONLY=0, LOW=1, DESTRUCTIVE=2) and `ChangePreview(target, risk, argv, …)` that guard consumes.
- `gamgui/core/connectors/gam_connector.py` — `_run_write(...)` audits (and serializes) almost every mutation. **One method skips it:** `create_onboarding_runbook` calls `self.audit.record("onboard_runbook", …)` directly, because it's a two-step tasklist build run straight through `runner.run_authenticated`. So `_run_write` is the *main* audit chokepoint, not the only `record()` caller — the allowlists `AUDITED_OUTSIDE_RUN_WRITE` / `READ_BY_CONTRACT` in `tests/test_command_contract.py` name every exception.
- **Callers of `enforce`** (each before its first GAM write): `builder.py` `/run` and `/sequence/run`; `users.py` `/suspend/apply` (destructive for suspend, LOW for unsuspend) and `/bulk/apply` (`confirm_step`); `calendars.py` `/event/delete` (destructive); `lifecycle.py` `/offboard/run` (declared destructive to the leaver — it locks sign-in and strips calendar access domain-wide, though each step is LOW); `signatures.py` `/apply` and `onboarding.py` `/run`, `/bulk/run` (`confirm_step`).
- **Not callers, on purpose:** single-target LOW writes (delegate, groups, vacation, org, calendar ACL, signature, sign-out, share/unshare, the groups board) — `evaluate` asks no confirmation for them; and account delete (`users.py` `/delete/apply`, type the exact email) and calendar delete (`calendars.py` `/delete`, type `DELETE`), whose own typed gates are stronger. The tripwire lists each with its reason.
- Templates post exactly `guard.CONFIRMED_FIELD`/`TYPED_FIELD`: the confirm buttons carry `hx-vals='{"confirmed": "1"}'` (or a hidden input in a `<form>`); `_sequence_preview.html` renders the typed `confirm` input when `requires_typed_confirmation`.

## How it works
`evaluate` takes `max_risk = max(p.risk for p in previews)` and `count = len(previews)`. Rules: destructive → always `requires_confirmation`; bulk (`count >= DEFAULT_BULK_THRESHOLD` = 10) of any non-read risk → confirm; destructive **and** bulk → `requires_typed_confirmation` (operator must type "confirm"); `count > DEFAULT_HARD_CAP` (200) → an `over_hard_cap` warning but not a hard block. It returns a `GuardDecision` that the preview template renders. The apply route then calls `enforce` with the same previews and `await request.form()` and refuses (an error partial, or the Builder's preview again) before any write. Separately, `_run_write` calls `self.audit.record(...)` on both the success and exception paths, writing one JSON line per mutation; `record` masks the argv through `redact_argv` and appends 0600 under a `threading.Lock`, rolling the file when it passes `max_bytes`.

## Invariants & the failure history
- **The check lives in the apply route, not the template (#2).** Five routes (suspend, bulk department, event delete, offboarding, signatures) once called `evaluate` only to draw the Confirm button and ran on a bare POST (failure-log 2026-09-23). A template's Confirm button proves nothing about the POST that comes back. Any new POST route fails `test_every_post_route_is_classified` until it is exempt-with-reason or GATED with a form the tripwire can post.
- **Chokepoint (#2):** guard sits between `ChangePreview` and `_run_write`, and `_run_write` audits every write that flows through it. The one live exception is `create_onboarding_runbook`, which runs its GAM calls via `runner.run_authenticated` and audits by hand — additive/low-risk, but a reminder that "everything is audited" holds only because that one path calls `record()` itself. Any *new* mutation must funnel through `_run_write` (or, like the runbook, record explicitly) so nothing mutates un-audited.
- **A write that never calls `record()` is invisible to a `record()` tripwire.** The Builder's `todrive` export (a new Sheet, in another user's Drive via `tduser`) and `reset_password`'s follow-up sign-out ran un-audited for exactly that reason (failure-log 2026-09-23). `test_every_run_authenticated_call_is_the_chokepoint_or_a_read` now checks every `run_authenticated(` call site instead; the export is audited as `export_to_sheet` (target = the Sheet's owner, or `(admin Drive)`), the sign-out as `signout_user`. Plain reads are not audited.
- **Redaction by value first, positional second (#4).** A caller that knows the secret passes it: `_run_write(..., secrets=[pw])` → `redact_secrets` masks every occurrence in the shown argv, the error text and the `ChangeResult.detail`, and `record(secrets=)` masks it again across the whole entry (target, argv, extra). Positional masking can't be trusted alone: a hire surnamed `Password` made `lastname Password password <pw>` spend the mask on the keyword, and the temp password GAM echoed on a usage error reached `extra.error` and the UI (failure-log 2026-09-23; `test_create_user_failure_redacts_password_by_value`). The second layer: `redact_argv` masks the value *after* any of `_SENSITIVE_KEYS = {password, notifypassword, signature, recoveryemail, recoveryphone, alternateemail}` (matching GAM's `key value` argv shape), and `errors._scrub_stderr` does the same for `password`/`notifypassword` in stderr. `create_user` also still audits a pre-built `"********"` argv (`audit_argv=`).
- **Rolling never loses in-window history.** `_roll_if_large` shifts generations oldest-first (`.9`→`.10` … `.1`→`.2`, then live→`.1`) so a roll only displaces the oldest of `RETENTION_GENERATIONS` (10); readers span all generations. Retention bound ≈ 10 × 16 MiB.
- **Readers snapshot generations against a mid-read roll.** `_open_generations` opens every generation up front and dedupes by `(st_dev, st_ino)`, so a roll landing mid-export can't make a long CSV export re-emit a drained file or skip one. `iter_records` streams newest-first and never materializes the whole log.
- **A filter must not pass `limit`.** `read_records`' docstring warns: capping before filtering would only ever show the newest slice and silently hide older matches.

## Gotchas / mock-lies traps
- Guard and `redact_argv` are pure Python over argv/previews — no GAM call — so `tests/fixtures/mock_gam.sh` and the vendored grammar are irrelevant to them. The route tripwire does use the mock, but only as an argv recorder: "zero writes" is trustworthy; its confirmed-path "the write ran" is as good as the mock's handler for that write.
- But the domain is only as safe as the `RiskLevel` each mutation declares (`DESTRUCTIVE`: `delete_user`, `delete_event`, `delete_calendar`, and `plan_suspend(..., suspend=True)`; almost everything else `LOW`; unsuspend is `LOW`). A mislabeled risk silently downgrades the confirmation the operator sees; that's a curation decision the tests here do NOT check — they assume the label is right.
- `redact_argv` is key-driven and positional: a *new* secret-bearing GAM flag not in `_SENSITIVE_KEYS` would be logged in the clear, and a value that spells a key shifts the mask. Adding a mutation that carries a secret means passing the value as `secrets=` **and** adding its key here.
- `secrets=` masks every occurrence, so a very short or common secret would mask ordinary text too — fail-closed by design. An empty string is ignored.

## Testing / live-verification status
`.venv/bin/python -m pytest -q tests/test_guard.py tests/test_write_routes_guarded.py tests/test_audit.py tests/test_audit_web.py` — fully offline, no tenant needed (pure functions + temp-file rotation with `max_bytes` shrunk to a few records via `_rotating_log`). Nothing in this domain touches a live domain, so nothing here needs live verification; the live risk lives one layer out, in whether each connector method passes the correct `RiskLevel` and a fully-redacted argv.

## To do common tasks here
- **New secret-bearing flag:** pass the secret value from the connector as `_run_write(..., secrets=[value])` (the primary layer); add its lowercase key to `_SENSITIVE_KEYS` in `audit.py` and a `test_redact_masks_*` case in `tests/test_audit.py`; add a failure-path test whose stderr echoes the command line (see `echoing_gam` in `tests/test_onboarding.py`).
- **Change a confirmation threshold/rule:** edit `DEFAULT_BULK_THRESHOLD` / `DEFAULT_HARD_CAP` or the boolean rules in `guard.evaluate`/`enforce`; update the assertions in `tests/test_guard.py`; if a route can now need the typed word, its confirm step must render the `confirm` input (else `enforce` refuses it always — fail closed); run `tests/test_write_routes_guarded.py`.
- **Add a mutating POST route:** build its previews (`plan_*` or `guard.changes`), call `guard.enforce(previews, await request.form())` before the first write, make its confirm step post `confirmed=1` (and `hx-disabled-elt` on the control), and add it to `GATED` in `tests/test_write_routes_guarded.py` with a bare form and its preview route. A single-target LOW write goes in `LOW_WRITES` there instead.
- **Change retention/rotation:** edit `MAX_LOG_BYTES` / `RETENTION_GENERATIONS` in `audit.py`; re-check `tests/test_audit_web.py` rotation and generation-spanning tests.
