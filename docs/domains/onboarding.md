# Domain: Onboarding

**One line:** The `/onboard` screen turns editable per-role runbooks into real actions for a new hire — create the Google account, apply the role's signature + OU, add them to the role's groups and subscribe them to its shared calendars, push a setup checklist to an assignee's Google Tasks, and send a welcome email — one hire at a time or in bulk from an uploaded CSV.

**Owns invariant(s):** the temp-password redaction rule (a specialization of invariant 2's audit chokepoint): the create-user password is never audited or surfaced. It leaves the app in exactly one of two ways — on the printable credentials sheet, or (when the row/form gives a `notify` address) in the sign-in email GAM/Google sends straight to that address; either way `password` and `notifypassword` are `***redacted***` in `audit.jsonl`. Also touches invariant 1 (argv-only, injection-safe steps/names) and invariant 9 (the bulk job's live feed is bounded).
**Enforcement home:** `tests/test_onboarding.py` — `test_run_executes_only_the_previewed_hire` (an account ticked, an address retyped or the welcome email added after Preview → zero writes), `test_run_uses_the_role_as_previewed`, `test_run_is_single_use`, `test_create_user_redacts_password`, `test_run_creates_account_and_returns_sheet`, `test_provision_hire_notify_vs_sheet` (asserts the pw is on the sheet / emailed but absent from `audit.jsonl`), `test_bulk_job_feed_is_bounded_at_scale` (#9), plus the argv-injection tests. No drift guard beyond the shared command-contract tests.

## How it works
Templates are the only local state: a role is `{steps, signature, org_unit, groups, calendars}` in `onboarding.json`; `RunbookStore._load` migrates an older bare-list-of-steps form (and dicts written before groups/calendars existed) via `_as_role`. `/preview` renders the plan and holds it — the form's values, the role template (`RoleTemplate`) and the welcome template as they are now — under a single-use token (`AppState.previews`, flow `onboard`) that its Run form posts back as a hidden `preview` input. `/run` (POST) first validates everything that doesn't write, then refuses without `confirmed=1` (`guard.enforce(..., confirm_step=True)` — every run writes, a task list at least; the preview's form posts it as a hidden input), then **runs only the previewed hire**: a missing, used or expired token, or a live form (`hx-include="#onboard-form"`) that differs from the previewed one in any field — "Create the Google account" ticked after a tasks-only preview, an email or assignee retyped — is refused with "preview again" and writes nothing (that is what gates account creation now; a stale "Create the task list" button once created a real account nobody had previewed, failure-log 2026-09-23). The role's steps, OU, groups, calendars and signature name, and the welcome text, are the held ones: saving the role again after Preview doesn't change what Run does. It then does the work in order: if `create_account` it generates a temp password, calls `conn.create_user(...)` (with `notify` when a delivery address is given, so GAM/Google emails the sign-in info directly), then best-effort `_apply_signature` (**only when this run created the account** — never for an existing hire); then — whenever an email is set, with or without account creation — best-effort `_apply_groups` and `_apply_calendars` (per-item failures collected, not fatal); then always `conn.create_onboarding_runbook(assignee, title, steps)`; then optionally `conn.send_welcome_email(...)`. `create_onboarding_runbook` creates the tasklist with `returnidonly`, reads the id off the last stdout line, and loops one `create task` per step — per-step failures are collected, not fatal.

**Bulk import.** `bulk/preview` parses an uploaded CSV (`parse_hire_csv`; columns = the single form's fields plus `notify`), validates each row's role against the store, and shows a confirm-gated summary. `bulk/run` (with `confirmed=1`, the same `guard.enforce` check) registers an `OnboardJob`, fires `_run_bulk_onboard` as an `asyncio.create_task`, and returns a partial that self-polls `bulk/status` every second (invariant 9: the `recent` feed is capped at `_RECENT_WINDOW`, the failed sample at `_FAILED_SAMPLE_CAP`; the credentials sheet renders in the final panel, not on every poll — served with `Cache-Control: no-store` and kept re-fetchable for `_CREDS_TTL` (15 min) or until the operator clicks Done (`POST bulk/done`), then dropped, so a refresh can't lose every password yet the plaintext doesn't linger). Each row runs the same `_provision_hire` as the single flow — so a blank `notify` puts the temp password on the printable sheet, a `notify` email hands delivery to GAM. The executor stops when an account create fails for a reason every later hire shares (`res["stop"]` → `web/jobs.py` `stop_reason`: sign-in expired, GAM not set up, a scope not granted), with "Stopped: … The remaining N were not attempted." in the final panel; a best-effort sub-step's failure (signature, a group, a calendar, the task list) never stops it, since the accounts themselves may still be created.

**Role-editor pickers.** The Groups and Shared-calendars fields each have a search box that HTMX-GETs `search/groups` / `search/calendars` (on `keyup changed delay:300ms, focus`) and swaps in `_onboard_picker.html`; clicking a result appends its address to the textarea (deduped, via `obAddToField`). Groups come from `AppState.groups()` (cached `gam print groups`) filtered by email/name; calendars come from `AppState.calendar_index.search(q)` but only when the index is built **and** belongs to the connected tenant (same domain check as `calendars._index_ready`) — otherwise the picker shows a "build the index" hint.

## Invariants & the failure history
- **Temp password never audited or surfaced.** `create_user` builds the real argv but passes a `"********"` copy as `audit_argv` to `_run_write`; `_run_write` records and previews `shown = audit_argv` and only feeds the true argv to the runner. The plaintext appears exactly once, in `_onboard_run.html`'s credentials sheet, and the account is created `changepassword on` so Google forces a reset at first login (`commit d78a1ef`).
- **argv-only (inv. 1):** every operator string — a runbook step, a name — is one argv element. Tests assert `"evil; rm -rf /"` and `"A; rm -rf /"` land intact as single elements. One element is still a *list* to GAM where the grammar says `<UserList>` (`"<UserItem>(,<UserItem>)*"`), so `looks_like_email` — used for the hire, the assignee and (in `users.py`) a new delegate — refuses a comma as well as a bare name.
- **Runbook write is serialized + audited but not via `_run_write`:** `create_onboarding_runbook` calls the runner directly (it needs the returned tasklist id and loops), then calls `self.audit.record` itself with the tasklist argv. It is still `serialize=True` and audited — not a rogue second write path, just a shaped one.
- **`render` substitutes only `WELCOME_VARS`** (`name/role/email/manager`); an unknown `{token}` is left literal, never crashes.

## Gotchas / mock-lies traps
- **The mock checks shape, not effect.** `tests/fixtures/mock_gam.sh` has a strict handler for every onboarding write (`create user` incl. the notify clause, `create tasklist`/`task`, `sendemail`, `signature`, `update group … add`, `add calendars`): an attribute keyword the grammar doesn't allow there fails with GAM's usage error, and anything unhandled fails. It still can't prove Google *accepts* the values (a real 409, a notify email actually sent) — `*exists*` mirrors the 409, `SENDFAIL` a bad recipient. Syntax source of truth: `gamgui/resources/gam7/GamCommands.txt` (`create task` ~L8824, `create tasklist` ~L8855, `sendemail`/`<MessageContent>` ~L5001).
- **`create task` takes the tasklist id positionally** (`<TasklistEntity>`), then `title` as a `<TaskAttribute>`; the id must come from the prior tasklist's `returnidonly` stdout. The mock only accepts the id its `create tasklist` handler returned (real GAM 404s an unknown id).
- **A malformed CSV is a row error, never a 500.** `parse_hire_csv` reads every record inside its `try`; a `csv.Error` (e.g. a cell over the module's 131,072-char field limit) refuses the whole file — the reader can't resume, and a half import would silently drop the rest. `bulk/preview` refuses an upload over `_MAX_CSV_BYTES` (1 MB) before decoding it (failure-log 2026-09-23).
- **The one-time sheet must be copyable, not only printable.** In the native window WKWebView can't print an iframe (pywebview replaces only the top-level `window.print`) and pywebview disables text selection, so a Print-only sheet could leave the operator with no way to take the password away. Each sheet has a **Copy** button (a plain-text version in a hidden, autoescaped `<textarea>`, copied by `copyEl` — async clipboard with an `execCommand` fallback); `obPrintSheet` prints from a hidden iframe in a browser and, under pywebview, prints the top-level page with a `@media print` rule that shows only the sheet. That native print path is **unverified in the built `.app`**; Copy is the path that must work.
- Temp-password alphabet excludes `0/O/1/l/I` on purpose (read off a printed sheet); don't "simplify" it back to a full alphabet.
- **A route test runs the single flow as the operator does:** `_preview_and_run` previews, then posts the preview's hidden `preview` token with the same form. A bare POST to `/onboard/run` with `confirmed=1` alone is refused — by design.
- **Never poll the bulk job's status endpoint in a loop under `TestClient`** (that hung CI). Route tests assert the polling panel appeared; completion is proven by calling `_run_bulk_onboard`/`_provision_hire` **directly** in an async test — or, to test through the route, `tests/helpers.py` `wait_for_job` awaits the task on the client's loop. See `docs/domains/web-screens-jobs.md`.
- **`notify` puts the temp password in the argv twice** (`password` and `notifypassword`). Both are masked because `create_user` passes the password as `secrets=` (masked by value everywhere, incl. the command line GAM echoes on a failure), audits a `"********"` copy, *and* `redact_argv` masks both keys — if you add another secret-bearing flag, do the same. The by-value layer is what holds for a hire surnamed `Password` (`test_create_user_failure_redacts_password_by_value`, `test_run_account_failure_error_partial_never_shows_password`).

## Testing / live-verification status
`tests/test_onboarding.py` runs fully offline (mock gam + in-memory Keychain, isolated `onboarding.json`/`signatures.json` under `tmp_path`). It proves store/CSV-parse/argv/redaction/flow-plumbing and — via direct `_provision_hire`/`_run_bulk_onboard` calls — the bulk executor and its bounded feed. **What still needs a real tenant:** that `create user` (incl. the `notify` sign-in email actually being sent), `user … create tasklist/task`, `sendemail to … html`, `user … signature … html`, `update group … add member`, and `user … add calendars` actually apply against live GAM — the mock cannot prove any of those, and per the house rule passing tests do not mean a GAM write works. Verify on a throwaway user before relying on the account-creation path.
