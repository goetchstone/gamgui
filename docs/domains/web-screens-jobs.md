# Domain: Web Screens & Jobs

**One line:** The FastAPI/HTMX screens (Users, Groups, Calendars, plus Lifecycle/Signatures) that render read-only pages and drive GAM mutations, and the tiny in-memory `BatchJob` registry that lets long per-user loops report polled progress instead of hanging the request.

**Owns invariant(s):** #9 (bound anything polled) — every live progress feed keeps a fixed rolling window and caps retained lists so a domain-wide run doesn't grow each 1s poll with the user count.
**Enforcement home:** `tests/test_write_routes_guarded.py` — every POST route refuses a bare POST with zero `gam` writes unless exempt with a reason, the confirm step each preview renders writes nothing when posted without its confirmation (token and all) and really runs the write when posted whole, a confirm step that posts the page's form runs nothing once that form is edited after the preview (`Case.edit`), and a replayed one writes nothing more; `tests/test_previews.py` pins the store itself. `tests/test_users_web.py` — the scale guards live there: `test_run_subscribe_bounds_its_log_at_scale`, `test_apply_job_record_stays_bounded_at_scale`, `test_signatures_apply_final_summary_caps_failed_list`, `test_batch_job_failures_stay_bounded_and_render_the_overflow`, `test_run_subscribe_caps_its_failed_sample`, and the source tripwire `test_no_route_appends_to_a_batch_jobs_failed_list_directly` (plus the cross-tenant `test_calendars_search_ignores_other_domains_index`). `tests/test_calendar_index.py` covers the persistent index itself (CRUD, atomic swap, owner-only file, scan), not the #9 guards. No drift-guard/hook — plain pytest.

## Files
- `gamgui/web/jobs.py` — `BatchJob` dataclass (`fail()` records a failure: full `failed_total`, a `failed` sample capped at `FAILED_SAMPLE_CAP`; `skipped` = offboarding steps not run because one they rely on failed) + `start_job(jobs, total, keep=10)`; the shared polled-progress record on `AppState.jobs`. `stop_reason(kind, remediation, left)` — the message a per-user loop stops with when a write fails with an account-wide kind (`ACCOUNT_WIDE_KINDS`: sign-in expired, GAM not set up, a scope not granted), else None.
- `gamgui/web/previews.py` — `Previews` on `AppState.previews`: what a confirm step may run. A preview route `hold(flow, form_key, value)`s the values it showed and renders the token into its confirm control (`preview` in `hx-vals` or a hidden input); the apply route `take(flow, token, form_key)`s them — single use, refused when expired (`PREVIEW_TTL`, 15 min) or when the live form no longer matches the previewed one — and runs the held values, never ones rebuilt from the live form. At most `PREVIEWS_KEPT` (8) per flow (#9).
- `gamgui/web/routes/users.py` — list/search/detail + actions (signature, delegate, groups, calendar ACLs, org/role, vacation, suspend via guard, delete, bulk set-department job — `_run_bulk_store`, `bulk_store.html` and the `store` form field keep their old internal names). A failed action says what didn't happen and GAM's remediation in words, with the raw error in `_action_result.html`'s collapsed "GAM's error" (`_failed`; delegation does the same through its `notice`).
- `gamgui/web/routes/calendars.py` — find calendar, ACL detail, event search/delete, secondary-calendar delete, share+subscribe fan-out job, persistent index rebuild job. `/share` resolves who it would subscribe *before* writing: a group of `guard.DEFAULT_BULK_THRESHOLD` (10) or more gets a confirm step in `_calendar_detail.html` naming the count (and the first ten members), holding the resolved members under a single-use token (flow `calendar_share_group`); its Confirm posts the live share form (`hx-include="#cal-share-form"`, which keeps the typed target and role) to `/share/group`, which takes the token, refuses a changed calendar/group/role, runs `guard.enforce(..., confirm_step=True)` and only then grants the ACL and starts the fan-out. It once started the fan-out straight from the Share button, whatever the group's size (a GATED case in `tests/test_write_routes_guarded.py`; the mock's `allhands@example.com` has 12 members).
- `gamgui/web/routes/groups.py` — drag-and-drop membership board (`/groups`); add/remove via `members_mutate`.
- `gamgui/web/templates/_bulk_apply.html`, `_calendar_subscribe_job.html`, `_calendar_index_job.html` — the self-polling HTMX partials.
- `gamgui/web/routes/signatures.py` — its own richer `ApplyJob`/`record()` (not `BatchJob`); the reference bounding implementation.

## How it works
Routes read from the cached directory (`request.app.state.gamgui.users()`) so pages/searches are instant; mutations are HTMX POSTs that swap a small result region. A long per-user loop (`_run_bulk_store`, `_run_subscribe`, `_build_index`) is fired with `asyncio.create_task`, its handle stashed on `job.task` (strong ref so it isn't GC'd), and the route returns a partial that self-polls a `.../status?job=<id>` endpoint on `hx-trigger="load delay, every 1s"` until `job.finished`, then renders a final panel with no more polling. `start_job` prunes the oldest finished jobs (keep=10) so the registry can't grow forever; `_lifespan` cancels any in-flight `job.task` on shutdown; the write it was running has its `gam` killed and is audited as interrupted (`_run_write`), not silently dropped.

## Invariants & the failure history
- **A per-user loop stops at a failure every later user shares.** `_run_apply` (signatures), `_run_bulk_store`, `_run_subscribe` and `_run_bulk_onboard` (on an account-create failure) read `ChangeResult.kind` after each write and, on an `ACCOUNT_WIDE_KINDS` kind, set `job.error` to `stop_reason(...)` ("Stopped: <remediation> The remaining N were not attempted.") and break; the final panel says so with how many were done. A per-target failure (not found, one refusal) keeps going. The signature loop once ran on through the whole company after the admin's sign-in expired, one identical failure per mailbox (failure-log 2026-09-23; `tests/test_bulk_stop.py`). Not these, on purpose: the Builder sequence (heterogeneous steps; a Gmail scope missing says nothing about the next step) and offboarding (its steps stop through `requires`).
- **#9, bounded polls.** `_run_subscribe` keeps `del job.log[:-_SUBSCRIBE_LOG_WINDOW]` (12 rows). `ApplyJob` caps `recent` at `_RECENT_WINDOW=12` and `failed` at `_FAILED_SAMPLE_CAP=200` while keeping full counts in `failed_total`; `BatchJob.fail()` does the same for every other job (bulk store, subscribe fan-out, builder sequence, offboarding), and the final panels print `failed_total` plus "… +K more" past the sample. These exist because a domain-wide run once made each 1s poll's HTML grow with the user count — and `BatchJob.failed` stayed an unbounded `.append` until 2026-09-23 (failure-log).
- **Guarded mutations (invariant #2) — checked in the apply route.** Suspend goes `plan_suspend` → `guard.enforce(previews, form)` → `conn.apply`; the bulk department job, event delete, offboarding, signature apply and onboarding call `guard.enforce` the same way before their first write (see `docs/domains/guard-audit.md` for the list and the exempt single-target LOW writes). The preview route renders the confirm step; the apply route refuses a POST without `confirmed=1` — five routes once ran on a bare POST because only the template asked (failure-log 2026-09-23). A confirm step that posts the page's live form (`hx-include`) also carries its preview's `web/previews.py` token, and the apply route runs the held values: the bulk department job sets the previewed department on the previewed people (their *current* titles, re-read from the directory; someone no longer active refuses the run), and a department, list or group edited after Preview is refused with "preview again" (the stale "Apply to 1 user" once wrote another department to more people, failure-log 2026-09-23). Calendar delete and user delete re-resolve/re-validate server-side and never trust the client-supplied identity (`_resolve_delete_owner`, exact-case `DELETE` / exact-email confirm).
- **No double submits.** Every control that starts a write or a job carries `hx-disabled-elt` (`"this"` on a button, `"find button"` on a `<form>`), so htmx disables it until the response lands — a double-click can't start two offboardings. `test_every_write_button_disables_itself_while_in_flight` checks every template control that posts to a write route. (The groups board's drag-and-drop posts via `htmx.ajax`, one request per drop.) **Trap:** the attribute is inherited, and `find …` resolves from the element making the request — so another htmx control inside such a form (the account-delete Cancel) finds nothing and htmx 1.9 throws on the null, killing that control. Give it its own `hx-disabled-elt="this"`; the same test fails otherwise.
- **Builder validation surfaces as a friendly error.** A share with a calendar role outside the grammar's `<CalendarACLRole>` makes `add_calendar_acl` / `add_calendar_acl_cal` raise `ValueError`; `/users/calendar/add` and `/calendars/share` catch it and render the amber partial with no `gam` call. Don't coerce a bad value in the route (`/calendars/share` once silently turned any unknown role into `reader`, while the other path passed it to GAM — failure-log 2026-09-23). `test_calendar_share_refuses_a_role_outside_the_grammar`.
- **Delegation checks the address before GAM.** GAM reads a delegate as a `<UserList>` — a bare name becomes `name@<domain>`, a comma targets two accounts — so `/users/delegate/add` runs `_check_delegate` first: not an address (`looks_like_email`, which refuses a comma), the owner itself, or an alias (it names the primary) is refused with no `gam` call; an address not in the cached directory, or a suspended one, renders a warning with **Add anyway** (`confirmed=1`) — a warning, not a block, because a minutes-old account isn't in the cache yet. Add/remove results and errors render *inside* `_delegates.html` (`notice`, with GAM's line in the disclosure), so the list and form never vanish behind an error. Remove asks first (`hx-confirm`), like the calendar-access Remove; both stay single-target LOW writes (failure-log 2026-09-23).
- **Cross-tenant safety.** `_index_ready` serves search only when `status.domain == audit_domain`; an index built for another tenant is treated as "needs rebuild" (`test_calendars_search_ignores_other_domains_index`).
- **Directory data into attributes (invariant #8):** templates put Google-sourced strings in autoescaped contexts; never `| tojson` in a double-quoted attribute.

## Gotchas / mock-lies traps
- **Placeholders and example data stay generic** (`example.com`, "Sales", "Training Calendar") — the public repo was de-branded once and the operator's company names crept back in via form placeholders and the seeded onboarding role. The local pre-commit hook's private-term tripwire (`.claude/private-terms`, gitignored) now blocks that. The UI says *Department*, never "store".
- **Record a failure with `job.fail(x)`, never `job.failed.append(x)`** — the append bypasses the cap (a source tripwire fails on it). `job.failed` is a *sample*: count with `failed_total`, not `failed | length`, and render "+K more" when `failed_total` exceeds it (`_bulk_apply.html`, `_calendar_subscribe_job.html`, `_sig_apply.html`).
- **A 200 proves nothing.** Every route answers 200 whether the write worked or not — a failure renders the amber error partial. Assert success with `tests/helpers.py`: `assert_ok_partial(r)` (no amber box), the `gam_calls` fixture + `gam_writes()` (the exact argv the mock received), and the audit record's `ok`. The mock fails any argv it has no handler for, so an unhandled write can no longer "succeed".
- **Never poll a job's status endpoint in a loop under `TestClient`** (that hung CI for 6h, before the fixtures were context-managed). To assert what a route-started job did, `wait_for_job(client, job)` awaits its task on the client's own loop, then render the status once; the signature apply, bulk store, offboarding and builder-sequence route tests do this. Other job routes (calendar share fan-out, index rebuild, bulk onboarding) still only assert the job started, with completion covered by executor tests.
- Share/subscribe, secondary-calendar delete, event delete, org/vacation writes are only exercised against `tests/fixtures/mock_gam.sh`. Per invariant #3 and CLAUDE.md "the mock lies," a mutation is unproven until run against a throwaway real tenant — check `gamgui/resources/gam7/GamCommands.txt`, not memory, for syntax (e.g. formatjson-reject quirks).
- Bare-address ambiguity: an ACL scope like `sales@example.com` may be a person or a group; `_subscribers_for` resolves it against the cached directory first (a known account is always a person) before a member lookup, because "member lookup errored" is a weak signal — mistaking a person for an empty group silently skips the subscribe that is the whole feature.

## Testing / live-verification status
`.venv/bin/python -m pytest -q tests/test_users_web.py tests/test_calendar_index.py`. Both use an in-memory vault + `mock_gam.sh` fixtures and a context-managed `TestClient`. Fully offline-proven: rendering, filtering/pagination, guard gating, confirm gates, cross-tenant index filtering, and the bounding invariants. **Not proven offline:** that any calendar/user/vacation/org/subscribe mutation actually succeeds on a live domain, and the polled loops running to completion under real GAM.
