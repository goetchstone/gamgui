# Domain: Web Screens & Jobs

**One line:** The FastAPI/HTMX screens (Users, Groups, Calendars, plus Lifecycle/Signatures) that render read-only pages and drive GAM mutations, and the in-memory job registry (`web/jobs.py`, one bounded `Job` base) that lets long per-user loops report polled progress instead of hanging the request — listed on every page by the header's jobs tray, with Stop (plan U5).

**Owns invariant(s):** #9 (bound anything polled) — every live progress feed keeps a fixed rolling window and caps retained lists so a domain-wide run doesn't grow each 1s poll with the user count.
**Enforcement home:** `tests/test_write_routes_guarded.py` — every POST route refuses a bare POST with zero `gam` writes unless exempt with a reason, the confirm step each preview renders writes nothing when posted without its confirmation (token and all) and really runs the write when posted whole, a confirm step that posts the page's form runs nothing once that form is edited after the preview (`Case.edit`), and a replayed one writes nothing more; `tests/test_previews.py` pins the store itself. `tests/test_users_web.py` — the scale guards live there: `test_every_job_record_stays_bounded_at_scale` (the base's bounds, for `Job`, `BatchJob` and `OnboardJob` alike), `test_run_subscribe_bounds_its_feed_at_scale`, `test_signatures_apply_final_summary_caps_failed_list`, `test_batch_job_failures_stay_bounded_and_render_the_overflow`, `test_run_subscribe_caps_its_failed_sample`, `test_each_bulk_feed_says_why_a_target_failed`, and the source tripwire `test_no_loop_appends_to_a_jobs_failed_list_directly` (it scans all of `gamgui/`, since some loops now live in core) (plus the cross-tenant `test_calendars_search_ignores_other_domains_index`). `tests/test_jobs_tray.py` — Stop on each loop through the strict mock (the exact argv that ran), the Stop route's refusals, the tray's bound and the job page. `tests/test_calendar_index.py` covers the persistent index itself (CRUD, atomic swap, owner-only file, scan), not the #9 guards. `tests/test_a11y.py` (`make a11y`, CI's `a11y` job) is the accessibility ratchet over every screen and a keyboard-only walk (below), and in the default run reads every template for an unnamed form field, a `[data-focus]` that can't take focus, a `focus:outline-none` with no `focus:ring-`, and a tab strip that isn't an ARIA tablist; `tests/test_contrast.py`, in the default run, holds every text colour in `app.css` to 4.5:1 on paper and white, and every fill under a white label. No drift-guard/hook — plain pytest.

## Files
- `gamgui/web/jobs.py` — the one bounded job base, `Job`: `record(item, ok, reason, detail)` counts one target (`done`, `applied`, `failed_total`), keeps a failure as an `Outcome` in the `failed` sample capped at `FAILED_SAMPLE_CAP` (200; `more` is the "+K more" past it), cuts its `reason` (the remediation in words) and `detail` (GAM's raw error) to `DETAIL_CAP` (300 chars), and rolls the live feed `recent` to the newest `window` rows (`RECENT_WINDOW`, 12); `finish()` sets `finished`/`finished_at`; `cancel_requested` is Stop's flag (plan U5, below); `interrupted` is offboarding's cut-off flag; `title` is what the tray calls a job and `kind` a `PANELS` key — the status route that renders its panel (`status_url`), whether it can stop (`can_stop`: every kind but `index`, one domain-wide read) and whether Stop asks first (`confirm_stop`: `offboard`). `BatchJob(Job)` adds offboarding's per-step `log` and `skipped`; `start_job(jobs, total, keep=10, window=12, title=, kind=)` registers one; `register_job` registers any job, pruning the oldest finished; `tray(jobs)` is the header's list — at most `TRAY_ROWS` (8), running first, then newest first — the running count and how many it leaves out. Signatures run a plain `Job`, onboarding its `OnboardJob(Job)`. The shared polled-progress record on `AppState.jobs`.
- `gamgui/core/bulk.py` — `stop_reason(kind, remediation, left)`: the message a per-user loop stops with when a write fails with an account-wide kind (`ACCOUNT_WIDE_KINDS`: sign-in expired, GAM not set up, a scope not granted), else None; `stop_requested(job)`: true, with `job.error` = "Stopped by you — N not attempted.", once Stop set `cancel_requested` (every loop asks it before each target); and `set_departments(job, conn, users, department)`, the bulk department loop (each person's title kept). Both moved out of `web/` (plan Q9); a loop in core fills the job it is handed and never imports `web/`.
- `gamgui/core/clock.py` — `now()`, a monotonic clock that counts time asleep (macOS `time.monotonic()` doesn't). Every TTL uses it: preview expiry, the directory cache, the Keychain secret cache, the onboarding credentials sheet.
- `gamgui/web/previews.py` — `Previews` on `AppState.previews`: what a confirm step may run. A preview route `hold(flow, form_key, value)`s the values it showed and renders the token into its confirm control (`preview` in `hx-vals` or a hidden input); the apply route `take(flow, token, form_key)`s them — single use, refused when expired (`PREVIEW_TTL`, 15 min) or when the live form no longer matches the previewed one — and runs the held values, never ones rebuilt from the live form. At most `PREVIEWS_KEPT` (8) per flow (#9).
- `gamgui/web/routes/users.py` — list/search/detail + actions (signature, delegate, groups, calendar ACLs, org/role, vacation, suspend via guard, delete, bulk set-department job — `_run_bulk_store` is the job's task: `bulk.set_departments`, then the cached directory is dropped; it, `bulk_store.html` and the `store` form field keep their old internal names). A failed action says what didn't happen and GAM's remediation in words, with the raw error in `_action_result.html`'s collapsed "GAM's error" (`write_failed`; delegation does the same through its `notice`).
- `gamgui/web/routes/calendars.py` — find calendar, ACL detail, event search/delete, secondary-calendar delete, share+subscribe fan-out job, persistent index rebuild job. `/share` resolves who it would subscribe *before* writing: a group of `guard.DEFAULT_BULK_THRESHOLD` (10) or more gets a confirm step in `_calendar_detail.html` naming the count (and the first ten members), holding the resolved members under a single-use token (flow `calendar_share_group`); its Confirm posts the live share form (`hx-include="#cal-share-form"`, which keeps the typed target and role) to `/share/group`, which takes the token, refuses a changed calendar/group/role, runs `guard.enforce(..., confirm_step=True)` and only then grants the ACL and starts the fan-out. It once started the fan-out straight from the Share button, whatever the group's size (a GATED case in `tests/test_write_routes_guarded.py`; the mock's `allhands@example.com` has 12 members). A failed `/unshare`, `/delete` or `/event/delete` answers with `write_failed` like the user-detail writes (they once headlined GAM's raw line).
- `gamgui/web/routes/jobs.py` — the jobs tray (plan U5). `GET /jobs/status` is the tray's list (`_jobs_tray.html`), polled every 2s from `base.html` on every page, with the header's "N running" badge out of band (`_job_live.html` `jobs_count`); `GET /jobs/<id>` (`job.html`) is a job's own page, whose panel loads from its `status_url` — the route that started it renders it, so nothing is duplicated (the index job's container is `#cal-index`, the id its panel targets); `POST /jobs/stop` sets `cancel_requested` and answers `_job_stop.html` in the button's place. It makes no GAM call (`LOCAL_ONLY` in the tripwire). `server.py` registers `jobs_tray(request)` as a Jinja global for `base.html`.
- `gamgui/web/routes/_common.py` — the helpers every screen shares, one copy each: `app_state`, `connector`, `friendly(exc, fallback)` (GAM's remediation, else the screen's own fallback line), `error_partial` (the amber `_action_result.html`), `write_failed`, `signature_store`, `NOT_CONNECTED`. They were pasted into each route module (seven `_friendly`s, five `_err`s) and had begun to drift; `test_route_helpers_live_once_in_common` fails on a new local copy.
- `gamgui/web/routes/groups.py` — the Groups board (`/groups`, plans U7 and A6). A group finder (`/search`) and the add field's type-ahead (`/people`) match address or name over the cached `st.groups()` / `st.users()` and render at most `PICK_LIMIT` (15), with "keep typing" past it — nothing renders the whole directory (the old board drew every user as a drag card and ran a live `gam print groups` on each visit). `/members` is a picked group's panel (`_group_panel.html`: heading, the add form, a member filter) and `/members/list` one page of `MEMBERS_PAGE` (50) members (`_board_members.html`: owners, then managers, then members; a role column; a nested group links back to the board; `/groups?group=` opens one directly, as a user's group chips do). Add (`POST /members`, a single-target LOW write) takes a role that `GAMCommands.add_group_member` validates — a `ValueError` becomes "Pick a role" with no `gam` call — and one full address: the field is free text and GAM reads the member as a `<UserTypeEntity>`, so `oauthuser` would add the authorizing admin, a bare name `name@<domain>` and a comma two people; add and remove refuse a group or member that fails `looks_like_email`, in words, before GAM. A member with no address (the domain-wide CUSTOMER row) has no Remove…. Remove is a confirm step: a row's Remove… posts `/members/remove/preview` (`_group_remove_confirm.html`, which warns before removing an owner) and its Remove posts `/members/remove`, which runs `guard.enforce(..., confirm_step=True)` first. A failed write re-renders the list with `_action_result.html` above it: what didn't happen and the remediation, GAM's error collapsed (plan U9). There is no drag-and-drop any more: every action is a form control. `groups.js` holds the finder's `aria-current` and the add field's ARIA combobox (below).
- `gamgui/web/templates/_bulk_apply.html`, `_calendar_subscribe_job.html`, `_calendar_index_job.html`, `_sequence_run.html` — the self-polling HTMX partials; `_job_failures.html`'s `failures(job)` macro is the final panels' failed list (item — reason, GAM's error in a `<details>`, "… +K more"). `_job_live.html` holds `stop(job, where)` — the Stop button in each running panel and tray row, "Stopping after the current one…" once pressed — and `ended(job, where)`, the same id on the finished panel's line (below).

## How it works
Routes read from the cached directory (`request.app.state.gamgui.users()`) so pages/searches are instant; mutations are HTMX POSTs that swap a small result region. A long per-user loop (`_run_bulk_store`, `_run_subscribe`, `_build_index`, offboarding's `lifecycle.run_offboard`) is fired with `asyncio.create_task`, its handle stashed on `job.task` (strong ref so it isn't GC'd), and the route returns a partial that self-polls a `.../status?job=<id>` endpoint on `hx-trigger="load delay, every 1s"` until `job.finished`, then renders a final panel with no more polling. `start_job` prunes the oldest finished jobs (keep=10) so the registry can't grow forever; `_lifespan` cancels any in-flight `job.task` on shutdown; the write it was running has its `gam` killed and is audited as interrupted (`_run_write`), not silently dropped. The registry is also the header's **jobs tray** (plan U5): a job survives navigating away — its row keeps its progress and final state, and its title links to `/jobs/<id>`, its panel — but not a quit (jobs live in memory).

## Invariants & the failure history
- **A per-user loop stops at a failure every later user shares.** `_run_apply` (signatures), `bulk.set_departments`, `_run_subscribe` and `_run_bulk_onboard` (on an account-create failure) read `ChangeResult.kind` after each write and, on an `ACCOUNT_WIDE_KINDS` kind, set `job.error` to `stop_reason(...)` ("Stopped: <remediation> The remaining N were not attempted.") and break; the final panel says so with how many were done. A per-target failure (not found, one refusal) keeps going. The signature loop once ran on through the whole company after the admin's sign-in expired, one identical failure per mailbox (failure-log 2026-09-23; `tests/test_bulk_stop.py`). Not these, on purpose: the Builder sequence (heterogeneous steps; a Gmail scope missing says nothing about the next step) and offboarding (its steps stop through `requires`).
- **Stop ends a loop between targets, never during one (plan U5).** A mis-scoped bulk apply once had no way to halt. Stop (`POST /jobs/stop`) only sets `job.cancel_requested`; each loop — `_run_apply`, `bulk.set_departments`, `_run_subscribe`, `_run_bulk_onboard` (between hires: one hire's every step runs), `_run_sequence` and `lifecycle.run_offboard` (between steps) — calls `stop_requested(job)` at the top of each iteration, so the write in flight finishes, is recorded and audited, and the run ends with "Stopped by you — N not attempted." Nothing cancels a task mid-`gam` (that is only a quit, `interrupted`). An offboarding marks the rest "– step — not run: stopped" (not `interrupted`) and its Stop asks first (`hx-confirm`, and the route refuses it without `confirmed=1`): stopping between the reset and the revoke leaves the leaver signed in. The calendar index rebuild has no Stop (one call, not a loop). `tests/test_jobs_tray.py` presses Stop during a write on each loop through the strict mock and checks the exact argv that ran.
- **#9, bounded polls.** Every job keeps its bounds in one place, `Job.record`: a `recent` feed of 12 rows, a `failed` sample of 200 with the full count in `failed_total`, 300 chars of reason and of raw error per failure. The final panels print `failed_total` plus "… +K more" past the sample. The three job types once each re-implemented this, with the constants defined twice (plan Q10); these exist because a domain-wide run once made each 1s poll's HTML grow with the user count — and `BatchJob.failed` stayed an unbounded `.append` until 2026-09-23 (failure-log). The Builder sequence sets `window` to its length (at most `MAX_SEQUENCE_STEPS`, 25) so every step keeps its row; offboarding's `log` is its eight steps.
- **Every failure says why (plan U9).** Each loop records the connector's `ChangeResult.remediation` as the reason and its `detail` as GAM's error: the live feeds (signatures, calendar fan-out, Builder sequence, bulk onboarding) show each `✗` row with its reason, and the final panels add GAM's error one click away. The bulk department, fan-out and sequence feeds once listed addresses with no reason.
- **Guarded mutations (invariant #2) — checked in the apply route.** Suspend goes `plan_suspend` → `guard.enforce(previews, form)` → `conn.apply`; the bulk department job, event delete, offboarding, signature apply and onboarding call `guard.enforce` the same way before their first write (see `docs/domains/guard-audit.md` for the list and the exempt single-target LOW writes). The preview route renders the confirm step; the apply route refuses a POST without `confirmed=1` — five routes once ran on a bare POST because only the template asked (failure-log 2026-09-23). A confirm step that posts the page's live form (`hx-include`) also carries its preview's `web/previews.py` token, and the apply route runs the held values: the bulk department job sets the previewed department on the previewed people (their *current* titles, re-read from the directory; someone no longer active refuses the run), and a department, list or group edited after Preview is refused with "preview again" (the stale "Apply to 1 user" once wrote another department to more people, failure-log 2026-09-23). Calendar delete and user delete re-resolve/re-validate server-side and never trust the client-supplied identity (`_resolve_delete_owner`, exact-case `DELETE` / exact-email confirm).
- **No double submits.** Every control that starts a write or a job carries `hx-disabled-elt` (`"this"` on a button, `"find button"` on a `<form>`), so htmx disables it until the response lands — a double-click can't start two offboardings. `test_every_write_button_disables_itself_while_in_flight` checks every template control that posts to a write route. **Trap:** the attribute is inherited, and `find …` resolves from the element making the request — so another htmx control inside such a form (the account-delete Cancel) finds nothing and htmx 1.9 throws on the null, killing that control. Give it its own `hx-disabled-elt="this"`; the same test fails otherwise.
- **Builder validation surfaces as a friendly error.** A share with a calendar role outside the grammar's `<CalendarACLRole>` makes `add_calendar_acl` / `add_calendar_acl_cal` raise `ValueError`; `/users/calendar/add` and `/calendars/share` catch it and render the amber partial with no `gam` call. Don't coerce a bad value in the route (`/calendars/share` once silently turned any unknown role into `reader`, while the other path passed it to GAM — failure-log 2026-09-23). `test_calendar_share_refuses_a_role_outside_the_grammar`.
- **Delegation checks the address before GAM.** GAM reads a delegate as a `<UserList>` — a bare name becomes `name@<domain>`, a comma targets two accounts — so `/users/delegate/add` runs `_check_delegate` first: not an address (`looks_like_email`, which refuses a comma), the owner itself, or an alias (it names the primary) is refused with no `gam` call; an address not in the cached directory, or a suspended one, renders a warning with **Add anyway** (`confirmed=1`) — a warning, not a block, because a minutes-old account isn't in the cache yet. Add/remove results and errors render *inside* `_delegates.html` (`notice`, with GAM's line in the disclosure), so the list and form never vanish behind an error. Remove asks first (`hx-confirm`), like the calendar-access Remove; both stay single-target LOW writes (failure-log 2026-09-23).
- **Cross-tenant safety.** `_index_ready` serves search only when `status.domain == audit_domain`; an index built for another tenant is treated as "needs rebuild" (`test_calendars_search_ignores_other_domains_index`).
- **Directory data into attributes (invariant #8):** templates put Google-sourced strings in autoescaped contexts; never `| tojson` in a double-quoted attribute.

## Gotchas / mock-lies traps
- **Placeholders and example data stay generic** (`example.com`, "Sales", "Training Calendar") — the public repo was de-branded once and the operator's company names crept back in via form placeholders and the seeded onboarding role. The local pre-commit hook's private-term tripwire (`.claude/private-terms`, gitignored) now blocks that. The UI says *Department*, never "store".
- **Record an outcome with `job.record(item, ok, reason, detail)`, never `job.failed.append(x)`** — the append bypasses the cap (a source tripwire fails on it). `job.failed` is a *sample* of `Outcome`s: count with `failed_total`, not `failed | length`, render `job.more` as "+K more" (the `failures` macro does), and compare names with `failed_items`.
- **A 200 proves nothing.** Every route answers 200 whether the write worked or not — a failure renders the amber error partial. Assert success with `tests/helpers.py`: `assert_ok_partial(r)` (no amber box), the `gam_calls` fixture + `gam_writes()` (the exact argv the mock received), and the audit record's `ok`. The mock fails any argv it has no handler for, so an unhandled write can no longer "succeed".
- **Never poll a job's status endpoint in a loop under `TestClient`** (that hung CI for 6h, before the fixtures were context-managed). To assert what a route-started job did, `wait_for_job(client, job)` awaits its task on the client's own loop, then render the status once; the signature apply, bulk store, offboarding and builder-sequence route tests do this. Other job routes (calendar share fan-out, index rebuild, bulk onboarding) still only assert the job started, with completion covered by executor tests.
- Share/subscribe, secondary-calendar delete, event delete, org/vacation writes are only exercised against `tests/fixtures/mock_gam.sh`. Per invariant #3 and CLAUDE.md "the mock lies," a mutation is unproven until run against a throwaway real tenant — check `gamgui/resources/gam7/GamCommands.txt`, not memory, for syntax (e.g. formatjson-reject quirks).
- Bare-address ambiguity: an ACL scope like `sales@example.com` may be a person or a group; `_subscribers_for` resolves it against the cached directory first (a known account is always a person) before a member lookup, because "member lookup errored" is a weak signal — mistaking a person for an empty group silently skips the subscribe that is the whole feature.

## Testing / live-verification status
`.venv/bin/python -m pytest -q tests/test_users_web.py tests/test_groups_board.py tests/test_calendar_index.py`. They use an in-memory vault + `mock_gam.sh` fixtures and a context-managed `TestClient`. Fully offline-proven: rendering, filtering/pagination, guard gating, confirm gates, cross-tenant index filtering, and the bounding invariants. **Not proven offline:** that any calendar/user/vacation/org/subscribe mutation actually succeeds on a live domain, and the polled loops running to completion under real GAM.

**Accessibility ratchet (plan A9).** `tests/test_a11y.py`, marked `a11y` and deselected from the default run: `make a11y` (or `.venv/bin/python -m pytest -m a11y -rP`) starts `scripts/preview_mock.py`'s app on a free port with a temp `$HOME`, drives headless Chrome at 1100×760 over `--remote-debugging-pipe` (`readme_screenshots.CHROME_FLAGS`, so `--use-mock-keychain`) through 21 states — Home, Users, user detail's four tabs, Groups with a group picked, its add field's suggestions open with one active and a member's remove confirm step, a signature preview, a calendar's access, a Builder `print groups` result, Onboard's four tabs, an offboarding preview and its finished run, Reports, Audit, Setup — injects the vendored axe-core 4.13.0 (`tests/a11y/`, SHA-256-checked) and counts serious/critical violations per screen and rule. `tests/a11y/baseline.json` holds today's: a new rule or screen or a higher count fails, and so does a lower one until the baseline is rewritten (`A11Y_UPDATE_BASELINE=1`), so a fix locks its gain in. At 2026-09-24 it held 487 nodes, 477 of them `color-contrast` (the nav links at 3.83:1 were 180; `text-brand-gray` at ~2:1 was 175; `text-brand-blueink/70` and `/80`, white on `brand-blue` buttons and `text-brand-blue` on paper the rest); plan A1 took that to 0, leaving 10: `select-name` 6 (Users' scope, user detail's group and calendar-role pickers, the groups picker, Calendars' role, the Builder's area), `label` 2 (the welcome-email body, the bulk CSV file input) and `label-title-only` 2 (Calendars' event date range); plan A4 named them all, so the baseline is empty (`{}`): any serious or critical violation now fails. Skipped without Google Chrome; CI's job sets `A11Y_REQUIRE_CHROME` so it fails instead. Moderate/minor findings aren't gated. axe sees the DOM, not WKWebView or a screen reader: a clean run is necessary, not sufficient.

**Keyboard and focus (plans A2, A4, A5).** The same module's `test_the_keyboard_alone_works_the_tabs_and_each_confirm_panel` sends real key events over CDP (`Input.dispatchKeyEvent`) and reads `document.activeElement`; with a page error trap it fails on any uncaught error too.
- *Tabs.* The user-detail and onboarding strips are ARIA tabs: `role=tablist` > `role=tab` (`id="tab-<name>"`, `aria-controls="panel-<name>"`, `aria-selected`) and `role=tabpanel` (`aria-labelledby`, `tabindex="0"`). `app.js` keeps a roving tabindex — only the selected tab is a Tab stop — and Left/Right (wrapping), Home and End select and show, as a click does (automatic activation: every panel is already rendered). The template renders the first tab selected.
- *Names.* Every `input`/`select`/`textarea` has a wrapping `<label>`, a `<label for>`, `aria-label` or `aria-labelledby` — a placeholder or `title` is not a name. Visible labels where the layout has room (vacation subject/message, the welcome email, the role editor, Calendars' event dates); `aria-label` on search boxes and one-line pickers. A Builder slot is a `div[data-slot]` with a `<label for="slot-<key>">` (a wrapping label may not hold the hint buttons), its help line wired by `aria-describedby`; `insertHint` finds the field through `[data-slot]`.
- *Focus.* A confirm/preview panel or an error that a click or submit swaps in carries `data-focus` on its heading (`tabindex="-1"`) or primary control (the account delete's typed address); `app.js`'s `htmx:afterSettle` handler focuses it and remembers the control that opened it per zone. A swap from `load`, polling, typing or a changed select never moves focus (the triggering event must be a click or submit). When the panel closes: a Cancel marked `data-cancel` (one that re-renders the zone with `hx-get`) or the `clear` action returns focus to the opener, or to its re-rendered twin (same tag and text — "Suspend…"); a Confirm or Run that replaced the panel leaves focus on the zone itself (`tabindex="-1"`), so its result is read. A panel whose error line is new puts `data-focus` on the error, not the heading.
- *The Groups board (plan A6).* Adding a member once needed a drag. Now every action is a control, and `test_the_groups_board_works_from_the_keyboard` runs them by keys alone: type in the finder, Tab to a group, Enter (focus lands on the panel's heading, the group gets `aria-current`); the add field is an ARIA combobox (`role=combobox`, `aria-expanded`, `aria-controls` → `#people-listbox`, `aria-activedescendant` on the active `role=option`) that `groups.js` drives — ArrowDown/Up move, Enter takes a suggestion without submitting (with none active it submits the typed address), Escape closes, and the count of suggestions goes to `#live-status`; a letter picks the role; after a successful add the message (`data-added`, `data-announce="group-board"`) is spoken and focus returns to the emptied field for the next person. A row's Remove… opens the confirm step at its heading, Cancel (`clear`) hands focus back to that Remove…, and Remove leaves it on the "Removed …" line. The test also reads Chrome's accessibility tree for the combobox, its options and the table's column headers. A pager button click focuses the list's count line.
- *Rings.* `base.html` gives every `:focus-visible` a 2px `#5A728E` outline; a text field swaps it for its own `focus:ring-2` (a class with `focus:outline-none` must also carry a `focus:ring-`). The walk tabs through twelve screens and fails a stop showing neither the brand outline nor a ring.

**Polled progress (plan A3).** A job panel swaps itself out every second, so it can't be a live region (a reader hears nothing, or the whole feed again). `base.html` holds the one that speaks, `#live-status` (`role=status`, polite, atomic, `sr-only`), outside every swap. Each render of a polled partial marks one element `data-announce="<job id>"`: `_job_live.html`'s `progress(job, label)` — a `hidden` span, "<label>: started", then "<label>: 30% done" in 10% steps — while it runs, and the result sentence once it's done (onboarding's is a hidden span that leaves the passwords out). `app.js`'s `htmx:afterSettle` handler copies that text into `#live-status` only when it changed for that job, so a poll that repeats a step says nothing. A feed or log row's ✓/✗ is `mark(ok)`: the glyph `aria-hidden`, then an `sr-only` "Succeeded:"/"Failed:" (offboarding's log lines come from core as "✓ …" strings; `log_line` splits them). `isPoll` in `app.js` treats every `…/status` request as a poll, so polls don't flash the `#busy` pill — itself a live region that said "Working…" each second. The Builder catalog row says its risk in words ("Read · …", "Destructive · …") beside the dot, which is `aria-hidden`. **The jobs tray (plan U5).** `base.html`'s Jobs button (`#jobs-toggle`, `aria-expanded`, `aria-controls="jobs-panel"`) is a disclosure: `app.js` opens it; Escape from inside closes it and returns focus to the button, and a click outside closes it. Polls keep focus: every state of a row's or panel's stop slot has the id `stop-<tray|panel>-<job id>` — the button, the focused "Stopping…" (`data-focus`), and at the end the result line (`ended`) — so htmx's same-id focus restore carries focus from Stop to the result. What it says: the running count is the button's text (its accessible name — "Jobs 2 running"), never announced by itself; a start is the operator's own click, which its panel announces ("<label>: started"); a finish is each finished row's hidden `data-announce="tray-<id>"` line ("Finished in the background: <title> — <result>."), which `app.js` speaks only when that job's own panel is not on the page — so it never talks over the panel's result, and a run that ends while you're elsewhere is still heard. `app.js` seeds `said` from the page at load, so a row that was already finished isn't news. `/jobs/status` is a `/status` path: `isPoll` keeps it off the `#busy` pill.
